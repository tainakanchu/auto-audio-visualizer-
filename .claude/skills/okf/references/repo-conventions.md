# 本リポジトリでの OKF 運用ルール

調査・検証で判明した事実を `knowledge/` バンドルに OKF v0.2 で記録する。

このファイルは**リポジトリの所有物**。導入後にチームの実情に合わせて自由に書き換えてよい。
`okf-init` を再実行しても上書きされない。

## なぜ記録するか

一つのリポジトリを複数人・複数エージェントが触ると、「調べた」「試して駄目だった」がチャットや
PR コメントに埋もれ、別の人・別のセッションが同じ調査を繰り返す。
OKF バンドルは**その再調査コストを削るためだけ**に存在する。

## 記録する / しない

**記録する**(再利用価値のある事実):

- 外部仕様・API の調査結果 — 特に**公式ドキュメントに書かれていない**実挙動
- 依存ライブラリ・データの癖・落とし穴 — バージョン差、文字コード、欠損、更新頻度
- 技術選定の根拠 — 検証した結果と、採用しなかった選択肢の理由
- 再現手順 — 環境構築・デバッグでハマった点とその回避策

**記録しない**:

- そのタスク限りの作業ログ(「ファイルを 3 つ直した」)
- コードを読めば分かること
- git 履歴・コミットメッセージに残ること
- CLAUDE.md や CONTRIBUTING.md に書くべき運用ルールそのもの

> 判断基準: **「3 日後の別の人が、これを読んで調査を省略できるか?」**
> No なら書かない。バンドルが膨らむと検索性が落ち、価値が下がる。

## ディレクトリ構成

```
knowledge/
  index.md              # 目次
  log.md                # 更新履歴
  tags.yml              # タグ語彙
  <concept>.md
  <subdir>/             # 例: specs/ decisions/ playbooks/
    index.md
```

サブディレクトリは必要になった時点で作る。**空のディレクトリを先に作らない。**
文書が数件のうちはルート直下に平置きでよい。

## ファイル名

`kebab-case.md`。内容が一目で分かる名前にする。日付やバージョンは名前に含めない
(frontmatter の `generated.at` / `stale_after` が担う)。

- 良い例: `graphql-pagination-limits.md`, `typescript-version-choice.md`
- 悪い例: `memo1.md`, `2026-08-18.md`, `調査結果.md`

## 本リポジトリでの `type` 値

`type` は自由だが、揺れると検索性が落ちるため以下に揃える。
足りなければ増やしてよい(未知の `type` は仕様上許容される)。

| `type` | 用途 |
| --- | --- |
| `Reference` | 外部仕様・API の調査結果 |
| `Dataset` | データ・スキーマの構造と癖 |
| `Decision` | 技術選定の根拠と、採らなかった選択肢 |
| `Playbook` | 再現手順・トラブルシュート |

## タグの語彙

`knowledge/tags.yml` がタグ語彙の唯一の定義元。
**書く前に登録済みタグの意味と使用頻度を確認し、そこに合わせる。**

```sh
cat knowledge/tags.yml   # 登録済みタグを分類・説明付きで一覧
```

タグは**複数文書を横断する検索の入口**であり、本文のキーワード列ではない。
製品名・API名など文書固有の語は全文検索で見つけられるため、原則タグにしない。

登録済み語彙で表せない場合は、近いタグへ統合できないかを先に検討する。
新しい横断軸が必要なら `knowledge/tags.yml` に `name`・`category`・`description` を追加してから使う。
現時点で1文書しかなくても、今後も使う安定した検索軸として必要性を説明できるなら追加してよい。
単なる本文キーワードの代替になるタグや、一覧へ未登録のタグは使わない。

タグ語彙は**運用の中で必要になってから**増やす。導入時点で網羅的に決めない。

## エージェントが書くときの必須事項

1. **`generated` を必ず付ける** — `{ by: <producer>/<version>, at: <ISO8601> }`。
   `by` は実行中の自分の producer 名とモデル/バージョンを実際に確認して書く
2. **`verified: { by: human:... }` を自分で付けない** — 人間のレビューを経て初めて付く
3. **`sources` に一次情報の URL を書く** — 「どこで確認したか」がないと再検証できない
4. **日付は実際に確認してから書く** — 推測で書かない。不明なら省略する
5. **`stale_after` を設定する** — 外部仕様の調査は陳腐化する。目安は 6 ヶ月後

### 日付は UTC で記録する

`generated.at` などのタイムスタンプは **UTC (`...Z`)** で書く。
人への説明ではローカルタイムを使ってよいが、記録は UTC に統一する。
表記が混在すると前後関係を比較しづらくなるため。

日付・日時の値は**引用符で囲む**。パーサによっては引用符なしの日付が `Date` に
変換され、validator の形式チェックが素通りするため。

### 日付の取得

推測で書かず、必ず実際の値を使う。

```sh
date -u +%Y-%m-%dT%H:%M:%SZ   # generated.at 用
date -u +%F                    # stale_after / last_modified 用
```

相対日付(6ヶ月後など)の構文は `date` の実装で異なる。手元がどちらかを確認してから使う。

```sh
date -u -v+6m +%F             # BSD (macOS 標準)
date -u -d '+6 months' +%F    # GNU (Linux / coreutils)
```

判定は `date --version` が成功するかで行える(成功すれば GNU)。

## 外部から取り込んだ文字列に注意

Web から抽出した題名などは**改行や制御文字を含むことがある**。
そのまま frontmatter に書くと YAML が壊れる。

- 取り込んだ値は**改行を空白に畳んでから**書く
- 迷ったら引用符で囲む — `title: "値"`
- **書いたら必ず検証する**(下記)。見た目では壊れていることに気づけない

## 書いたら検証する

```sh
pnpm knowledge:check
```

## 更新のしかた

**既存の記述が誤りと判明した場合は、追記ではなく修正する。**
誤った記述が残っていると、それ自体が再調査コストになる。

内容が古くなったが履歴として価値がある場合は `status: deprecated` にし、
本文冒頭に後継へのリンクを置く(公式サンプルの慣例に合わせる)。

大きな変更をしたら `log.md` に 1 行足す。

## テンプレート

```markdown
---
type: Reference
title: <一目で分かる題名>
description: <一文で要約>
tags: [<登録済みタグ>]
status: stable
generated: { by: <producer>/<version>, at: "<ISO8601>" }
sources:
  - id: <キー>
    resource: <一次情報の URL>
    title: <出典名>
    last_modified: "<YYYY-MM-DD>"
stale_after: "<YYYY-MM-DD>"
---

# 結論

<最初に結論。読み手が調査を省略できるだけの情報を書く>

# 根拠

<どう確認したか。実行したコマンドと出力があれば載せる>

# 注意点

<ハマりどころ、例外条件>
```
